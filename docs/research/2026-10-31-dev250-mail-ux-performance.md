# DEV-250: responsive mail composition and workflow research

Researched 2026-10-31 against public primary sources. Macro source is pinned to commit `426b009f6f16264f46a8f4a9155666f4e3c84150`, resolved from its public main branch through GitHub API. Source was downloaded for inspection only; no foreign code was executed or copied into the implementation. No mailbox, credentials, message contents or authenticated browser state were accessed. Altitutor implementation diagnosis is separate from this research.

## Findings verified in Macro source

### Editing and saving are separate lifetimes

Macro's autosave captures the editor snapshot on each edit, immediately queues its local persistence, then debounces network persistence by **500 ms**. Writes are serialized with `queue.then(write, write)`, so a failed save does not poison subsequent saves. Local writes coalesce pending snapshots behind an active write. It exposes local save status and flushes/retries pending local data on visibility change and disposal. Cancellation explicitly removes scheduled work; disposal uses the captured snapshot rather than reading a disappearing editor. These are actual code behaviors, not general claims of speed. [draft-autosave.ts](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-compose/primitives/draft-autosave.ts#L5-L128)

Draft persistence mints a stable local handle before first dispatch and tracks a session epoch. Outcomes from a draft abandoned through send/discard/reset cannot install an old identity into a newer composer. It distinguishes deterministic rejection from transport failure. This is useful evidence for retaining identity/revision guards; Altitutor need not reproduce Macro's whole local storage scheme. [draft-persistence.ts](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-compose/primitives/draft-persistence.ts#L34-L102)

### Refresh should not dismantle an active editor

Macro deliberately does **not invalidate the active thread query on draft save**, because its Suspense subtree can detach and reset the editor and scroll. It marks the affected thread and removes inactive cached queries; cleanup invalidates the marked thread later. This is more precise than saying Macro performs no refetches. [draft-cache.ts](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/lib/queries/email/draft-cache.ts#L4-L22)

The compose adapter still refreshes preview lists and the relevant collection entity in the background. It catches presentation errors separately from successful draft writes. Delivery refreshes the affected thread and scheduled messages rather than remounting every mail surface. [compose-adapter.ts](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-compose/compose-adapter.ts#L128-L145), [post-save handling](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-compose/compose-adapter.ts#L427-L454), [schedule settlement](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-compose/compose-adapter.ts#L663-L690)

Thread draft reconciliation retains newer known draft data over older responses, retains locally open drafts omitted by a stale response, and tracks locally deleted drafts separately so delayed responses do not resurrect them. This supports a stable editable working copy layered over server observations. [thread-drafts.ts](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-thread/primitives/thread-drafts.ts#L5-L101)

### Dismissal means accepted work, not confirmed delivery

In the pinned implementation, reply submission first saves the necessary draft snapshot, then calls delivery, and **clears the editor only after durable acceptance resolves**. A rejected admission preserves/restores the matching mounted editor; later cache/navigation refresh is detached and separately reported. The architecture prose's broader optimistic-clearing wording is therefore insufficient to describe this exact code. Do not infer that merely clicking Send or starting a fetch is durable acceptance. [reply-composer.ts](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-compose/primitives/reply-composer.ts#L1190-L1450)

Macro's immediate-send adapter freezes message, attachments, signature and working-copy version into an attempt, persists it in a local journal, then returns its attempt ID. Its cancellation/status paths distinguish cancellation pending, sending/sent, and delivery unconfirmed. An unconfirmed outcome does not authorize automatic resend. [send-queue.ts](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/lib/queries/email/send-queue.ts#L71-L229)

Dispatch and recovery run from the authenticated application session, rather than the mounted composer. Therefore closing a composer does not own or cancel delivery. This is the reusable lifetime principle; an additional browser outbox is not required merely to improve Altitutor's modal responsiveness. [outbox-session.ts](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/lib/queries/email/outbox-session.ts#L23-L87)

### Recipient chips and signatures

Macro's mail-specific recipient input reuses its shared selector for known contacts and custom addresses, with mail styling and Escape behavior. [compose-recipient-input.tsx](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-compose/components/compose-recipient-input.tsx#L8-L25)

The underlying selector validates comma/semicolon-terminated address lists, deduplicates case-insensitively, converts known/custom addresses into selected recipient objects, and commits the highlighted choice on Tab while its menu is open. This is a real tokenized completion model, not a comma-separated free-text field with a visual border. [RecipientSelector.tsx](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/lib/core/component/RecipientSelector.tsx#L727-L778), [keyboard handling](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/lib/core/component/RecipientSelector.tsx#L1004-L1055)

Signature previews sanitize HTML, isolate markup in a Shadow Root, constrain images, and set safe external-link attributes. A signature is a separate optional/collapsible preview, preventing the app's CSS reset from destroying pasted formatting. [signature-preview.tsx](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-compose/components/signature-preview.tsx#L7-L78)

Macro explicitly detects HTML structures/attributes its rich text editor cannot round-trip and offers HTML editing for them. This shows why an editor migration must not silently flatten existing complex signatures. [signature-html.ts](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/settings/core/signature-html.ts#L1-L82)

### Schedule selection is not a confirmed schedule

Macro separates an editable time choice from the confirmed schedule and delivery status. Submit validates a future time, saves the draft, then commits scheduling; failure reconciles authoritative lifecycle state before claiming failure or success. Updating a confirmed time does not rewrite its locked body. Cancellation unlocks editing only after confirmation; sending/unconfirmed schedules cannot be casually cancelled. A failed post-schedule archive is reported separately. [email-send-schedule.ts](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-compose/primitives/email-send-schedule.ts#L13-L43), [submit](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-compose/primitives/email-send-schedule.ts#L307-L410), [cancel](https://github.com/macro-inc/macro/blob/426b009f6f16264f46a8f4a9155666f4e3c84150/apps/web/src/features/email-compose/primitives/email-send-schedule.ts#L495-L559)

## Official Superhuman product evidence

Superhuman's Outlook signature workflow explicitly permits pasting the existing signature **including images and hyperlinks**, and recommends copying from Outlook web when desktop copying damages formatting. Signature inclusion on replies/forwards is configurable. This supports rich signature editing/paste and preview as a product direction; the documentation does not expose Superhuman's internal renderer, persistence or sanitization design. [Signatures](https://help.superhuman.com/hc/en-us/articles/46005771841933-Signatures)

Its Send Later workflow offers suggested times and a typed custom time. Smart Send is a distinct recipient-specific recommendation; it can cancel to a draft when an optional no-reply condition no longer holds. These product features do not prove any particular server scheduling transport or latency. [Schedule email instructions](https://help.superhuman.com/hc/en-us/articles/47206763851533-Switching-from-Notion-Mail-to-Superhuman-Mail), [Smart Send](https://help.superhuman.com/hc/en-us/articles/46005572688525-Smart-Send)

Official documentation distinguishes provider-synchronized drafts/read state from client-owned workflow features such as Send Later and snippets. Do not present a portal-local schedule as necessarily editable in Outlook or identical to Outlook's own scheduling mechanism. The cited article describes Gmail delegation specifically; it does not establish Outlook integration behavior. [Delegation and synchronization](https://help.superhuman.com/hc/en-us/articles/47464280644621-Executive-Assistants-Working-in-Gmail-via-Delegation)

## Minimal recommendations for Altitutor

These are design recommendations derived from the evidence, not claims about currently implemented behavior:

1. **Keep typing local and immediate.** One composer session owns the current envelope/body/attachments plus a revision. Debounce serialized background Graph saves around 500–800 ms; use the latest returned changeKey for the next save. Do not disable typing for routine saves, and never overwrite newer edits with an older save/poll response. Show quiet Saving/Saved/Save failed feedback. Flush before send and when leaving the draft. If restart recovery is required, use an explicit scoped persistence policy; do not silently put shared business correspondence into long-lived browser storage.
2. **Patch affected cache entries, then revalidate quietly.** A draft save or read/assignment mutation should update its known thread/list representation without a global loading state or active composer remount. Refresh only affected thread/list keys in the background. Preserve list scroll/selection and accessory tabs. Existing provider sync remains the convergence path; faster UX does not require rewriting mailbox sync or reducing every polling interval.
3. **Detach sending from dialog lifetime without weakening correctness.** Preserve the flushed provider draft and frozen command/attempt identity, own the in-flight operation outside the mounted dialog, and let the dialog dismiss while a global pending status remains inspectable. Distinguish admission, submission, and Sent confirmation. If the existing API only returns after provider submission, a client may show a provisional Sending state while retaining the draft and request, but must not claim durable queued acceptance prematurely. A network failure after submission is unresolved, not a new send opportunity. Cache-refresh failure must never change an accepted send into a retryable delivery error. Reuse the existing database send registry and reconciliation.
4. **Reuse native recipient controls.** Add recipient tokens with completion, custom valid addresses, keyboard commitment/removal and accessible labels. Keep typed addresses distinct from committed tokens; validate all To/Cc/Bcc at save/send. Preserve the development recipient allowlist. Reuse the portal's existing searchable-select/popover primitives rather than importing Macro UI.
5. **Preserve HTML through editing and delivery.** Use the existing portal rich-text/editor conventions where they round-trip the required content. Store sanitized HTML with a plain-text fallback, retain the signature separately or snapshot it once at send, and preview its actual formatting. Test pasted links/images and avoid appending a signature on every autosave. Received-email HTML needs its own sanitized renderer; rendering arbitrary raw HTML is not a substitute.
6. **Make scheduling a real delivery workflow if in scope.** Keep selected and server-confirmed time separate; use a durable server-owned schedule/claim and existing send registry, never a browser timer. Lock the approved scheduled content and make edit/cancel a confirmed state transition. Show Scheduled/Submitting/Unconfirmed/Sent accurately and reconcile Outlook/provider activity; never retry an uncertain send just because the time passed. Cosmetic toolbar controls alone are insufficient.

Suggested behavioral evidence: type continuously during delayed saves; deliver two save responses out of order; poll while editing; close/reopen an accessory tab; fail one background save; send with delayed cache refresh; dismiss then observe an uncertain send; reopen without enabling duplicate send; paste rich signature and multiple recipients; schedule/cancel across reload. Use fake provider latency/error controls first, then controlled Exchange correspondence under the established test-mailbox scope.
