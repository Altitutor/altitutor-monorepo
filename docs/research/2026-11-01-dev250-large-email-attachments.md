# DEV-250: large email attachments, progress and preview

Researched 2026-11-01 from Microsoft and Vercel primary documentation plus the current checkout. No account, mailbox configuration, credentials, private runtime files or environment files were inspected. No implementation or provider writes were performed. The recommendations below are design judgments, not verified tenant behavior.

## Answer and limits

**Files above 3 MB are supported.** Graph uses ordinary attachment POST for smaller files and upload sessions for 3–150 MB files. Upload sessions accept sequential byte ranges, enabling resumable transfer. Creating a session for a message supports application `Mail.ReadWrite`, so the existing app-only permission model does not need a broader permission just for larger attachments. [createUploadSession](https://learn.microsoft.com/en-us/graph/api/attachment-createuploadsession?view=graph-rest-1.0).

The Graph upload ceiling does not establish the size of an email that can be sent. Exchange Online defaults are 35 MB sending and 36 MB receiving; administrators can configure different mailbox limits up to 150 MB, with more restrictive client/transport/attachment rules possible. External mail incurs roughly 33% encoding expansion, and all attachments share the whole-message budget. Recipient-side restrictions still apply. [Exchange Online limits](https://learn.microsoft.com/en-us/office365/servicedescriptions/exchange-online-service-description/exchange-online-limits#message-limits).

Recommendation: initially support **20 MB aggregate raw attachments per message**, including existing attachments, and at most that size for one file. This is a conservative portal policy allowing ordinary files above 3 MB while leaving room under common 35 MB send defaults; it is not a delivery guarantee or a measured tenant limit. Make the policy configurable after a mailbox-limit check. Do not label 150 MB as the usable send limit.

The known shared/delegated-mailbox upload-session issue is specifically documented for **delegated permissions**, which return 403 outside the signed-in user's mailbox. It does not establish a general prohibition on the current app-only shared-mailbox path. Verify that path with the scoped development mailbox. [Graph known issues, large-file attachments](https://learn.microsoft.com/en-us/graph/known-issues#calendar).

## Current code facts

- `apps/admin-web/src/app/api/email/attachments/route.ts`: one multipart request reads the entire file, rejects `file.size >= 3_000_000`, checks staff access/draft version and the existing edit claim, then creates base64 and adds the attachment.
- `apps/admin-web/src/features/email/server/graph.ts`: `addAttachment` independently rejects base64 strings longer than 3,900,000 characters. Thus some raw files below the UI's 3 MB boundary already fail near 2.925 MB. The Graph helper serializes JSON with the mailbox bearer token and a 15-second timeout; an opaque upload URL requires a **separate binary transport**, not reuse of that helper.
- `EmailComposer.tsx`: attachment queue serializes with saving, but stores names only for uploaded chips; it does not reload the provider's attachment list for existing drafts. Removal exists through `removeAttachment` and an Undo toast. Use provider IDs, rather than names or array indices, as chip identity.
- `attachments/route.ts` GET already lists provider metadata and proxies raw `/$value` download, forcing octet-stream and attachment disposition. Existing thread attachment links use this route. Reusable portal preview primitives exist at `src/shared/components/files/FilePreviewModal.tsx` and `src/shared/hooks/useFilePreview.ts`; assess reuse before adding another viewer.

## Recommended transport

Use **sequential binary chunks of 1,966,080 bytes (six × 320 KiB, about 1.875 MiB) through authenticated Next routes**, retaining the small-file path for files below Graph's boundary. Vercel Functions document a 4.5 MB request/response payload ceiling; raising a route's local validator does not remove it. Binary chunks stay comfortably below the request ceiling and avoid base64 overhead. [Vercel Function limits](https://vercel.com/docs/functions/limitations#request-body-size). The raw Outlook guide demonstrates 2 MiB ranges without a multiple rule, but Microsoft's SDK Outlook example explicitly requires the maximum slice size to be a multiple of 320 KiB. Six multiples satisfies that guidance and stays below Outlook's 4 MB ceiling; the final remainder is shorter. [SDK Outlook example](https://learn.microsoft.com/en-us/graph/sdks/large-file-upload?tabs=csharp#upload-large-attachment-to-outlook-message).

Proposed flow:

1. Start: authenticate staff, verify configured mailbox/draft/edit claim, filename/size and aggregate budget; create the Graph upload session. Return a short-lived opaque upload handle plus expected offset/expiry, not a mailbox access token.
2. Chunks: browser sends raw `File.slice()` bytes and range to the portal. Resolve the handle server-side, bind it to staff + mailbox + draft + edit token + total bytes + expiry, and reject arbitrary caller-supplied upload URLs. Validate bounded chunk length and expected range; forward only to the provider-minted HTTPS session URL. Never add the Graph Authorization header to upload-session requests. Serialize mutations and renew/check the existing edit lease throughout a multi-request upload; merely claiming once at session creation is insufficient.
3. Persist only session metadata/capability, not a duplicate attachment file. Prefer a short-lived **service-role-only upload-session table** holding a random public handle, staff/mailbox/draft/edit identity, file metadata, expected offset, expiry, lifecycle state, final attachment ID and encrypted upload capability. Claim/advance offsets atomically and serialize per draft; include active uploads in the scheduled-send admission guard. Keep the capability inaccessible to authenticated clients, remove it on finalization/cancellation/expiry, and reconcile ambiguous completion before starting another session. A process-memory map alone cannot span Vercel instances. Do not log session handles, upload URLs, authorization material or request payloads. Send `private, no-store` on session responses.
4. Finalize: after provider completion, confirm attachment metadata in the configured draft, refresh the observed message/changeKey, invalidate attachment metadata, and only then show Attached/re-enable send. Keep upload success separate from email delivery success.

Direct browser-to-Microsoft upload is an alternative that avoids proxy bandwidth. Microsoft's JS SDK supports browser use and large-upload tasks, progress callbacks and the returned Outlook Location. [JS SDK](https://github.com/microsoftgraph/msgraph-sdk-javascript), [LargeFileUploadTask](https://github.com/microsoftgraph/msgraph-sdk-javascript/blob/dev/docs/tasks/LargeFileUploadTask.md). It requires giving the browser a preauthenticated capability and proving CORS, readable completion headers and cancellation from the deployed origin. It also bypasses per-chunk portal edit checks. Given this app's guarded shared drafts, chunk proxying is the simpler correctness boundary; do not expose the app's Graph token for direct upload.

## Protocol details and cancellation

The Outlook-specific guide requires binary `PUT` with `Content-Type: application/octet-stream`, `Content-Length`, and inclusive `Content-Range: bytes start-end/total`; keep chunks below 4 MB. Do not send Authorization. Intermediate success is 200 with `nextExpectedRanges`; final success is **201 with an empty body and a Location header containing the attachment ID**. Store that ID for preview/removal. Do not assume a DriveItem JSON response. A separate DELETE to the original session URL cancels an unfinished upload and returns 204, also without Authorization. Observe the returned expiry; the Outlook guide says it remains unchanged through PUTs. [Outlook large-attachment protocol](https://learn.microsoft.com/en-us/graph/outlook-large-attachments).

Cancellation must abort the in-flight client request and ask the server to cancel the provider session. If the last chunk raced with cancellation, reconcile the draft before claiming removal: cancelling a completed session is not deleting a completed attachment. For an attached file, use Graph's attachment DELETE and the existing draft guard. A failed/ambiguous final response must trigger metadata reconciliation before retrying from scratch, preventing duplicate attachments. [Delete attachment](https://learn.microsoft.com/en-us/graph/api/attachment-delete?view=graph-rest-1.0).

The Microsoft JS upload-task implementation performs `getStatus()` with GET on the original upload-session URL and `resume()` uses that before continuing; it also tolerates Outlook property casing variations (`nextExpectedRanges`/`NextExpectedRanges`, `expirationDateTime`/`ExpirationDateTime`). [Microsoft SDK source](https://github.com/microsoftgraph/msgraph-sdk-javascript/blob/dev/src/tasks/LargeFileUploadTask.ts). The raw Outlook guide does not separately specify GET-status permissions/response, so prove GET/DELETE on an app-only-created scoped session rather than relying on OneDrive behavior. These use the preauthenticated capability transport, not `/users/...` plus the Graph bearer. Never forward the app token to `outlook.office.com`, follow redirects without validation, or fetch a client-supplied Location URL. Extract the final provider attachment ID and verify it through the configured mailbox/draft's Graph attachments endpoint. Missing/unparseable Location remains Finalizing/unconfirmed until metadata reconciliation identifies the new provider object; filenames alone do not identify it.

Use the earliest returned expiry as a safe bound: the generic uploadSession resource mentions extension on fragments, whereas the Outlook-specific guide says expiry remains unchanged. Resume only from confirmed provider offsets, not an increment based solely on bytes sent by the browser. Enforce the 20 MB budget server-side at start and send admission, including all draft attachment types/inline bytes and outstanding reservations; use a conservative size estimate rather than assuming Graph metadata `size` is always identical to raw file bytes. Leave explicit room for the body, signatures and MIME overhead. No settings change or relaxed tenant limit is implied.

## Preview, progress and removal UX

Maintain attachment items with local queue ID, provider ID when known, name/type/size, state (queued/uploading/finalizing/attached/error/cancelled), confirmed bytes and cancellable request. Show per-file progress and a durable remove control. Count only provider-acknowledged bytes as confirmed; show Finalizing rather than Attached until metadata/version refresh succeeds. Existing draft attachments must load from Graph, so reopening preserves preview/removal. Support removing queued files, cancelling uploading files, and confirmed deletion of attached files as distinct operations. Block send/schedule/discard while the owned attachment operation is unresolved; preserve body/recipients throughout.

Preview local images/PDF/text using short-lived browser object URLs before upload; revoke URLs on removal/unmount. For persisted attachments, Graph supports raw file contents via `/$value`; item attachments return MIME and cloud reference attachments are a different type. [Get attachment](https://learn.microsoft.com/en-us/graph/api/attachment-get?view=graph-rest-1.0). Reuse the portal preview shell, allowlist suitable preview types, and offer download for unsupported formats. Do not render arbitrary HTML/SVG inline on the privileged app origin or pass private mail attachment URLs to public document-viewer services.

Large persisted preview/download can use the existing authenticated raw streaming proxy. Vercel's specific guidance for oversized response bodies explicitly recommends streaming functions, which are exempt from the 4.5 MB response-body limit. [Vercel streaming exception](https://vercel.com/kb/guide/how-to-bypass-vercel-body-size-limit-serverless-functions#if-the-response-body-is-too-large). Node streaming became default for Pro/Enterprise deployments in 2024. [Node streaming announcement](https://vercel.com/changelog/streaming-now-enabled-by-default-for-all-node-js-vercel-functions). Next documents returning `new Response(ReadableStream)` for streaming, and NextResponse extends Web Response; therefore `new NextResponse(upstream.body, ...)` is the appropriate form, an inference from those contracts. [Route streaming](https://nextjs.org/docs/app/api-reference/file-conventions/route#streaming), [NextResponse](https://nextjs.org/docs/app/api-reference/functions/next-response). Keep the response streaming end-to-end; do not first call arrayBuffer/blob/json or set a fabricated Content-Length. Retain staff authorization, no-store, allowlisted preview content types, cancellation/backpressure and a finite transfer timeout. The current Graph helper's 15-second timeout also covers body consumption and may need a download-specific allowance. Deployed verification of a >4.5 MB incompressible file with byte/hash comparison remains necessary; this is a runtime check, not an architectural blocker requiring a new file store.

The Graph attachment GET documentation supports raw `/$value` but does not document HTTP Range or a preauthenticated `downloadUrl` for fileAttachment. The fileAttachment resource lists contentBytes/content metadata, unlike DriveItem's download capability. [Get attachment](https://learn.microsoft.com/en-us/graph/api/attachment-get?view=graph-rest-1.0), [fileAttachment resource](https://learn.microsoft.com/en-us/graph/api/resources/fileattachment?view=graph-rest-1.0). Do not invent either guarantee or expose the Graph bearer to bypass the proxy. A range-emulating portal endpoint could read/discard an upstream prefix and return a bounded slice, cancelling afterward, but would repeatedly fetch prefixes and needs exact length/version validation to implement HTTP semantics correctly. It is unnecessary given the documented streaming exception. Load a whole bounded 20 MB file to a transient browser Blob for preview when a viewer would otherwise require unsupported provider range requests.

Required focused evidence: below/above boundary files; 20 MB aggregate validation including existing attachments; duplicate filenames; multi-file queue progress; cancel before/during/final chunk; interrupted/resumed transfer; expired session; lease loss; ambiguous final response; reopen and preview/delete; malformed URL/range rejection; deployed large download; scoped app-only provider upload without send unless separately authorized.


## Implementation decision for this pass

The implementation reuses `email_draft_edits`, whose active write lease already excludes save, send, schedule and discard, instead of adding a second session table. Authenticated chunk requests atomically swap an operation token; a short-lived AES-GCM ticket binds the provider capability to staff, mailbox, draft, version, byte total and lease token. The existing runtime client secret derives the ticket encryption key; no new secret setup is required. This is an implementation choice rather than a Microsoft guarantee. Provider-confirmed ranges control progress; failed chunks are never automatically replayed, and cancellation rereads the draft to reconcile a possibly completed final request. Abandoned requests may hold the draft for up to ten minutes before the lease expires. There is no automatic resume across a page reload in this pass.

The user approved a 20,000,000-byte aggregate attachment budget. Progress reports browser transport bytes with a finalizing state until Microsoft confirms the updated draft. Attached files, including reopened drafts, support preview and guarded removal; cancellation of a queued/in-flight file from the UI is deferred. The composer blocks send and close during its current upload queue. Preview supports PDF and raster images in the shared file dialog, with download for other types. No message delivery or tenant-size-limit increase is needed to test uploads.
