## What is missing or narrower than it first appears

- Import does not request/store folder membership, Graph read state, flags/categories, HTML, attachments, reply headers or distinct To/CC/BCC. To and CC are flattened. Drafts and delta removals are skipped; there is no deletion or move reconciliation. Direction is inferred solely from `from === admin@altitutor.com`. See [`mailbox-sync.ts:102–129`](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/apps/admin-web/src/features/onboarding/server/mailbox-sync.ts#L102-L129).
- `last_error` exists but the importer only clears it on successful page saves; the route returns exceptions without persisting sync failure. No explicit stale-cursor recovery, overlap lease, throttling/backoff or webhook/subscription lifecycle appears in this module. Ten-page bounding applies to messages; folder discovery occurs beforehand.
- `ignored` is a local onboarding-review decision, not an Exchange archive/delete action. Read/sent labels are imported inference, not delivery receipts.
- No email send/reply/forward or Graph mutation route was found. README wording says drafts open a staff mail application, but current onboarding communication code has only message/note composition and no `mailto` draft implementation; treat that wording as stale documentation.
- Existing `Composer` and `useSendMessage` are telephone/iMessage-specific: sender IDs come from `owned_numbers`, destinations are phone/Apple ID handles, sends insert queued `messages` then invoke the `send-message` function. An email address there may mean an **iMessage Apple ID**, not SMTP email. See [`mutations.ts:17–152`](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/apps/admin-web/src/features/messages/api/mutations.ts#L17-L152). Avoid making Exchange a pretend owned phone number.
- No focused mailbox-sync tests were found under `apps/admin-web/src`. This is a future verification seam, not evidence the existing importer is broken.

## Existing domain and UI seams

**Business messages retain their domain owners.** Invitation, registration, booking and invoice endpoints call canonical builders. For example, [`send-invoice/route.ts:160–211`](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/apps/admin-web/src/app/api/invoices/%5Bid%5D/send-invoice/route.ts#L160-L211) builds/sends an invoice notification and records `invoice.notification_sent`. UCAT lifecycle/transactional email has its own suppression, consent, outbox/ledger and Resend webhook processing. A mailbox should expose correspondence and context without silently replacing those workflows or their eligibility rules.

**Activity has a deliberate contract.** [ADR 0036](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/docs/adr/0036-drive-admin-activity-and-automation-from-lifecycle-events.md) requires explicit immutable lifecycle events, direct entity links, recorded/effective times and transactional deduplication/automation enqueueing. [`activity.ts:87–108`](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/apps/admin-web/src/features/activity/api/activity.ts#L87-L108) reads `vadmin_domain_event_feed` by recorded time. The original [`domain_events` schema](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/supabase/migrations/20260830223000_explicit_domain_events.sql#L201-L260) requires UUID subjects and approved subject/entity types; imported Graph IDs are text. A general email subject cannot simply be inserted without a deliberate model change. Mixed communication feeds already provide a seam for correspondence without turning every synchronization update into a lifecycle event.

**Notification read state is a different domain.** [ADR 0011](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/docs/adr/0011-shared-app-scoped-notification-inbox.md) defines recipient-specific, app-owned notifications. That does not determine the shared mailbox's read/handled/assignment policy. Reusing notification state as mail read state would conflate personal alerts with shared operational work.

**Authentication must be checked at the action boundary.** The existing mailbox route verifies active ADMINSTAFF before taking service access. The commonly imported [`requireAdminStaff.ts:28–34`](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/apps/admin-web/src/features/pay-tiers/server/requireAdminStaff.ts#L28-L34) checks role without explicitly checking status; use the active-admin RPC pattern for privileged mail actions rather than inheriting this weaker helper accidentally. Portal layout access alone is not the action check.

**Reuse the shell before extending the transport.** [`EntityCommunicationPanel`](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/apps/admin-web/src/features/activity/components/EntityCommunicationPanel.tsx#L87-L134) and [`MessagesView`](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/apps/admin-web/src/features/messages/components/MessagesView.tsx#L336-L357) provide entity-centered conversation layout; `MessageThread` accepts independent timed feed entries. [`SettingsDataTable`](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/apps/admin-web/src/shared/components/settings-data-table.tsx#L38-L64) and `useDataTable` supply table/toolbar/filter conventions, but the implementation filters loaded data in memory and should not be assumed to provide whole-mailbox search. [`commandPalette.config.ts:6–20`](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/apps/admin-web/src/features/command-palette/config/commandPalette.config.ts#L6-L20) documents navigation and shared `QUICK_ACTIONS` seams; adding searchable email entities is a separate RPC/search integration.

## Recommended boundaries and remaining product decisions

Create a mailbox-owned capability under `features/email` (or agreed domain name), with server-side Graph authentication/sync/commands, normalized mailbox/message identity, local workflow metadata and explicit entity links. Retain onboarding as a consumer/projection. Reuse layout and feed presentation, not the phone transport contract. Preserve the provider-neutral renderer and canonical business notification builders required by [ADR 0024](https://github.com/Altitutor/altitutor-monorepo/blob/298c6e695e4167d4e6d3726e09979de0d87388f7/docs/adr/0024-centralised-email-presentation-and-message-ownership.md); freeform correspondence needs an explicit presentation decision rather than accidentally overriding canonical templates.

The repository cannot answer these choices:

1. Is the first release a replacement for daily Outlook work or a contextual shared support queue? Which reply/forward/new-mail, attachment and HTML capabilities are essential?
2. Is `admin@` the only mailbox and sender identity? Does founder mail belong here? Existing code proves neither extra mailbox access nor permission.
3. Which state is authoritative/shared: Exchange read/archive/folders, local handled/assignment/snooze, or both? What does one admin reading mail do for another admin?
4. Should email-to-student/parent matches be suggested, automatic, or explicitly confirmed? Address-based matching currently spans all correspondence, and shared parent addresses create multi-student ambiguity.
5. Must existing automated Resend mail appear in the mailbox and support threaded replies? That is a reconciliation requirement, not supplied by a shared From address.
6. Which mutations must sync back to Outlook, how much history should initial import cover, and what freshness/outage behavior is acceptable?

These are product choices to grill after the external Graph capability research. No implementation direction is recorded as accepted by this audit.
