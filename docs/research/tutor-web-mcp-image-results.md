# Tutor-web MCP image results

Date: 2026-07-29

Protocol status checked on that date: MCP `2026-07-28` is the newest specification revision. Its image, embedded-resource, and resource-link tool-result forms remain the same as `2025-11-25`; the newer revision's major breaking changes concern the stateless core and request metadata rather than image content. The tutor-web server's current `@modelcontextprotocol/sdk`/handler compatibility should be evaluated separately before opting into that revision. ([MCP 2026-07-28 release notes](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/), [official TypeScript SDK revision guidance](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28))

## Question

Why can AI clients not see the images returned by the tutor-web UCAT authoring MCP server, and what should the server return instead?

## Conclusion

This is primarily a server-result-shape problem, with a client-compatibility caveat.

MCP natively supports actual image tool results. A `tools/call` result may contain an `ImageContent` block whose `data` is the bare base64-encoded image and whose `mimeType` identifies the format. The server does **not** need to make the model fetch a URL, and it cannot send an unencoded binary frame in a normal MCP result because the protocol message is JSON-RPC. The standard representation for inline image bytes is:

```json
{
  "content": [
    {
      "type": "text",
      "text": "Generated image preview."
    },
    {
      "type": "image",
      "data": "<base64 bytes, without a data: prefix>",
      "mimeType": "image/png"
    }
  ]
}
```

The MCP specification explicitly permits mixed content items in tool results and gives this base64 image shape as the image result representation. It separately defines resource links and embedded resources. ([MCP tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#tool-result))

The current tutor-web server does not emit an MCP image block:

- `generateUcatMcpImage` and `reviseUcatMcpImage` upload the generated bytes, then return metadata whose document node points at a signed URL ([`media.ts`](../../apps/tutor-web/src/features/ucat/mcp/server/media.ts#L32), [`media.ts`](../../apps/tutor-web/src/features/ucat/mcp/server/media.ts#L63)).
- `getUcatMcpFile` also returns only metadata and a one-hour signed URL ([`media.ts`](../../apps/tutor-web/src/features/ucat/mcp/server/media.ts#L134)).
- Most importantly, the common `jsonResult` wrapper serializes every successful value into a `type: "text"` content block plus `structuredContent`; it has no branch that can emit `type: "image"` ([`register-tools.ts`](../../apps/tutor-web/src/features/ucat/mcp/server/register-tools.ts#L91)).
- The server advertises only the tools capability, not resources ([`route.ts`](../../apps/tutor-web/src/app/api/mcp/route.ts#L20)).

Therefore a client currently receives a URL *described in JSON*. Whether it subsequently downloads that URL and promotes it to an image input is entirely client-specific. A model saying it cannot access the image is expected behavior; the server has not returned an MCP image.

## The three relevant MCP representations

### 1. `ImageContent`: use for an image the model should inspect now

Shape:

```json
{
  "type": "image",
  "data": "<base64>",
  "mimeType": "image/png"
}
```

This is the most direct and interoperable semantic signal: the result item is an image, not text containing a URL. The OpenAI Agents SDK officially states that, for locally managed Streamable HTTP/SSE/stdio MCP integrations, it automatically maps MCP image content to image tool-output entries and forwards mixed text/image results as multiple output items. ([OpenAI Agents SDK MCP documentation](https://openai.github.io/openai-agents-python/mcp/#mcp-tool-outputs-text-and-images))

That OpenAI statement demonstrates real client support, but MCP does not force every host to render or submit every content type to its model. A conforming server can emit `ImageContent` while a particular client, model, or product surface still handles it poorly. Client behavior should therefore be verified per target (ChatGPT, Codex, Agents SDK, Claude, and so on).

For ChatGPT/Codex plugins, OpenAI's current first-party server guide says `content` may contain text or other MCP content that helps the model answer, and instructs developers to verify tool results in MCP Inspector and then test the same flows in ChatGPT developer mode. It does not document any promise that a URL appearing inside text or structured JSON will be downloaded as an image. ([OpenAI plugin MCP server guide](https://developers.openai.com/plugins/build/mcp-server#return-useful-results-without-ui), [testing guidance](https://developers.openai.com/plugins/build/mcp-server#run-and-test-locally))

### 2. Embedded resource: use when returning resource contents inline

An embedded resource is a `type: "resource"` content block whose `resource` contains either `text` or a base64 `blob`, plus a URI and MIME type. The schema says it is up to the client how to render an embedded resource for the LLM or user. ([MCP schema source](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2025-06-18/schema.ts#L3581-L3600))

For images intended for immediate vision, `ImageContent` is clearer than an embedded binary resource. An embedded blob is useful when the object is fundamentally a file/resource or when one result can contain several non-image binary formats, but client promotion of a generic blob into model vision is less certain.

### 3. `resource_link`: use for deferred or large content

A tool may return a `resource_link` URI for the client to fetch. A link returned by a tool need not appear in `resources/list`. ([MCP tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#resource-links))

If the URI is meant to be read through MCP, the server implements the resources capability and responds to `resources/read`. Binary resource contents are returned as a base64 `blob` with a MIME type. ([MCP resources specification](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#reading-resources), [binary resource contents](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#binary-content))

The resource specification specifically says an `https://` resource URI should be used only when the client can fetch the resource directly from the web without reading it through the MCP server; otherwise the server should prefer another or custom URI scheme. ([MCP resource URI guidance](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#https))

This makes a stable MCP-owned URI such as `altitutor-file://<file-id>` (exact scheme is an application decision) safer than treating an expiring Supabase URL as an MCP resource identity. On `resources/read`, the server can authorize the caller, download the current object, and return its bytes. However, a resource link is still less reliable for immediate vision because the client must decide to follow it and then decide how to expose the returned blob to the model.

## Why signed URLs are fragile here

A signed URL can work as an ordinary OpenAI image input: OpenAI's vision guide accepts either a fully qualified URL or a base64 data URL as image input. ([OpenAI images and vision guide](https://developers.openai.com/api/docs/guides/images-vision#giving-a-model-images-as-input))

That does not mean a URL embedded in an MCP tool's text result is automatically turned into an image input. The MCP host would need to:

1. recognize that the string is an image URL;
2. trust and fetch the origin;
3. fetch it before the signature expires;
4. survive redirects, network egress rules, SSRF defenses, and content-type checks; and
5. add the downloaded object to the next model request as image content.

Those steps are outside the guarantee made by the current tool result. OpenAI's remote MCP security guidance also warns applications to treat URLs and image URLs from MCP tool outputs cautiously and to trust their domains before embedding them. ([OpenAI MCP safety guidance](https://developers.openai.com/api/docs/guides/tools-connectors-mcp#urls-within-mcp-tool-calls-and-outputs))

Signed URLs remain useful for a human preview or download UI, but they should be supplemental metadata, not the only model-visible image representation. They are bearer capabilities, so avoid logging or persisting them more broadly than necessary.

## Recommended tutor-web design

### Immediate change

For `generate_ucat_image` and `revise_ucat_image`:

1. Keep the generated/revised PNG bytes available until the handler creates the MCP result.
2. Return a short text block plus an MCP `ImageContent` block containing `bytes.toString("base64")` and `mimeType: "image/png"`.
3. Keep stable metadata (`fileId`, `alt`, storage identity, and the authoring `imageNode`) in `structuredContent`.
4. A signed URL may remain in `structuredContent` for human UI convenience, but do not rely on it for model vision.
5. Do not put the base64 in the text block or `structuredContent`; that wastes textual context and loses the image semantic type.

This requires either a specialized image-result helper or a generalized result type. The existing `jsonResult` helper cannot represent media.

### Reading an existing stored image

For stored images, prefer one of these, in order:

1. A narrowly scoped read tool that returns the selected image directly as `ImageContent`, with ordinary metadata alongside it. This is the best compatibility path when the model explicitly needs to inspect a known image.
2. Add MCP resources with a stable, authorization-checked file URI and return a `resource_link` for large/deferred files. Keep a direct image-read tool as a fallback because automatic resource following varies by client.

Do not make the model parse rich-text JSON, discover a signed `src`, and fetch it independently.

### Payload controls

Base64 expands binary data by roughly one third, and the whole result still travels inside JSON-RPC over stdio or Streamable HTTP. MCP defines the JSON-RPC transport but not one universal payload ceiling; client, SDK, proxy, serverless platform, and model-input limits can all be lower. The official MCP Ruby SDK, for example, defaults stdio frames and Streamable HTTP request bodies to 4 MiB and notes that this corresponds to roughly 3 MiB of base64-decoded payload; it also states this matches the TypeScript SDK's default. ([Official MCP Ruby SDK request-size documentation](https://github.com/modelcontextprotocol/ruby-sdk#request-size-limits))

Practical server policy:

- validate decoded bytes and MIME type;
- allow only known raster formats for inline vision (PNG/JPEG/WebP as supported by target clients);
- resize or recompress oversized source images into a model-facing derivative;
- set a conservative inline-byte ceiling (for example, around 2 MiB initially, then tune from observed client limits);
- return dimensions, original size, derivative size, and a stable file ID in metadata;
- use a resource link or a clear error when a safe inline derivative cannot be produced;
- never inline the current 50 MiB revision maximum as base64.

The protocol uses the same JSON content model regardless of whether the transport is stdio or HTTP. Changing transport does not by itself make a URL visible to the model. MCP still carries JSON-RPC protocol messages in the current revision. ([MCP transport specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports))

## Compatibility test matrix

Before considering the issue fixed:

1. Call the tool in the official MCP Inspector and confirm the raw result contains `content[].type === "image"`, valid bare base64 data, and the correct MIME type.
2. Test a small known image with visible text/shapes in each supported client and ask a question that cannot be answered from the alt text.
3. Test mixed text + image results.
4. Test expiry-independent behavior by omitting the signed URL from one test result.
5. Test the configured maximum size and verify the server returns a derivative or explicit error rather than a truncated/corrupt base64 string.
6. If a client still cannot see a valid `ImageContent` result, record that as a client/product limitation and use that client's documented upload/file-input route as its fallback.

## Decision

Return native `ImageContent` for generated, revised, and explicitly fetched images. Treat the signed URL as optional UI metadata. Consider MCP resources later for large/deferred assets, but do not use `resource_link` as the sole path for images the model must inspect immediately.

## Implementation status

Implemented in tutor-web on 2026-07-29:

- generated and revised images return native MCP image content after durable storage;
- `get_ucat_file` returns native image content for accessible stored images;
- deterministic SVG visuals are rasterised for MCP model inspection;
- model-facing images are limited to 2 MiB decoded and 1600 pixels on either axis, with WebP derivatives used when required; and
- signed URLs and stable authoring metadata remain in `structuredContent`, while base64 bytes remain only in typed MCP `content`.
