# Autosave work items with field conflict checks

AdminWeb tasks, issues, projects and documents open ready to edit after their saved content loads. The shared editor autosaves user changes as conditional field patches. Record reads, form resets, rich-text hydration and changes to editability never initiate writes. Selectors save immediately; title and rich-text edits debounce for 600 ms. Saving leaves the editor writable, serializes requests, and retains newer edits until their own request succeeds.

Each patch includes only changed properties and their original persisted values. The database checks those expectations under the record's transaction lock, so concurrent changes to different fields can both succeed. A stale change to the same field returns its conflict and the latest saved record without applying the patch. The editor keeps local content visible, stops retrying that field, and allows unrelated properties to save. Users can choose the latest value or explicitly replace it with their own; replacement still checks the reviewed value, so intervening edits produce another conflict. Project membership is checked using the same aggregate representation as reads.

The normal UI shows save status without View/Edit, Save/Cancel, live unsaved previews or draft/version management. One automatic recovery copy per user and record in each browser tab retains unsaved field changes, expectations and uncertain requests across reloads. Recovery never rebases expectations onto newer content automatically. Same-key retries reconcile HTTP failures that occur after commit before sending subsequent changes. Closing or replacing a record flushes pending edits and prompts only when they cannot save; abrupt tab closure is guarded while changes remain unsaved. Recovery is browser-session storage and does not promise survival after the browser tab is permanently closed.

The conditional patch delegates validation, attribution, audit history and guarded writes to the established work-item database functions. Audit history remains an internal safeguard rather than an editing workflow. New editors hold no persistent lease; short transaction leases preserve existing write guards and compatibility with board/MCP actions. Older clients that still hold a live lease must close or expire before a patch can write. This change ships through the normal migration CI/CD path.
