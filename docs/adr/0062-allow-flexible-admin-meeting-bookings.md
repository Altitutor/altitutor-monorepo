# Allow flexible admin meeting bookings

DEV-203 centralises six manual meeting types in AdminWeb into People, Schedule, and Preview/confirm. Matthew explicitly chose flexible participant mixes and counts instead of preserving the previous type-specific cardinality and staffing restrictions. The meeting type describes intent; it does not constrain the participant tables in this admin workflow. Optional messaging follows successful booking, and new staff interview candidates default to Trial.

AdminStaff may select arbitrary dates, times and durations. Declared availability, opening hours, capability/subject mismatches, blockouts, active sessions, buffers and reservations produce advisory warnings. A warning lookup failure also permits proceeding. Valid timestamps and references, authorization and database integrity remain enforced, including the Subject required for Drafting billing.

Use an authenticated, active-AdminStaff, security-invoker transaction to create the Session and all assignments together. Reusing the single-student booking RPC would retain restrictions Matthew rejected; separate client-side inserts would risk partial bookings. Public and self-service booking APIs retain their existing rules. Rescheduling preserves Session identity and durable links, hydrates the existing roster before confirmation, and retains removed staff assignments as planned absences. Existing students must be removed through the established Log absence workflow so the administrator explicitly chooses billing treatment; the booking form does not silently choose one. Recurring Class, Homework Help and Admin Shift scheduling remains outside this flow.

Family associations drive optional Add suggestions in both directions. Selecting an attendee neither silently adds family members nor changes family relationships. Check-in conducting/receiving and staff interview candidate roles remain available as assignment metadata without imposing participant combinations.
