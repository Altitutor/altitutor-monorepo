# Codex UCAT authoring MCP

Codex accesses UCAT authoring through a remotely hosted Streamable HTTP MCP server authenticated by Supabase OAuth, rather than a local stdio server or a service-role credential. Supabase OAuth dynamic client registration is enabled so supported Codex clients can register themselves and present the normal consent screen without brittle per-client callback configuration. OAuth tokens preserve the acting tutor's `auth.uid()` identity and existing role façade for attribution and authorization across Codex desktop, CLI, and IDE clients; the MCP server validates that tokens target its own resource, and database changes required for the integration ship only through CI/CD. Passing the existing `is_ucat_tutor()` authorization check is sufficient to use MCP; there is no additional staff allowlist. The MCP endpoint is hosted inside the tutor-web deployment as an isolated bearer-authenticated adapter over shared server-side UCAT authoring services, while tutor-web's cookie-authenticated routes and embedded agent use those same services rather than duplicating domain logic; a separate deployment is deferred until scaling or isolation requires one. The MCP server is an additional client alongside tutor-web's embedded authoring agent, not its replacement. MCP tools may create drafts, edit draft or in-review content, and explicitly submit drafts for review; they must reject publishing, editing published content, deleting or restoring top-level content at the server-side authorization boundary. Eligible MCP mutations execute directly without a second confirmation or server-side staging layer because draft and in-review lifecycle restrictions already provide the safety boundary; revision checks, validation, and audit recording still apply. A valid mutation of in-review content preserves its `in_review` status so review-time fixes do not trigger an implicit lifecycle transition; MCP never publishes automatically. Nested composition edits may add, reorder, update, or remove lesson blocks, questions, answer options, stems within sets, and sets within mocks. Creates accept a complete initial aggregate, while updates accept explicit typed add, update, move, and remove operations so omission never deletes nested content; each operation batch is validated and committed atomically against the supplied revision. Drafts may be incomplete, but every save must preserve structural integrity and valid references; submission for review and every mutation of in-review content must pass the aggregate's full readiness validation. Read access covers learning modules, question-stem bundles, question sets, and mock exams in every lifecycle state and access scope, plus the sections, categories, tags, referenced files, generation runs, and AI assessments needed to author them; student, attempt, class, billing, and other operational data remain outside the MCP boundary. Deleted aggregates may be retrieved read-only and are omitted from searches unless `includeDeleted` is explicitly requested. Question authoring supports both the existing durable AI generation pipeline and direct structured generation by Codex: pipeline requests retain their established prompts, gates, budgets, visuals, run tracking, and review behavior, while directly created Codex bundles are recorded with AI-generation provenance and begin as drafts until explicitly submitted for review. V1 image authoring exposes the existing server-backed generation, revision, and deterministic-rendering pathways with preview-first results and revision-guarded attachment to eligible content. Importing bitmap files produced by Codex's client-side image generator is deferred because MCP has no portable client-local binary upload mechanism; a shell and short-lived-upload workaround would behave inconsistently across Codex clients and sandbox policies. Learning module folders remain outside the lesson lifecycle: MCP may create or edit a folder only while it has no published descendant lesson, and must treat folders participating in the live Learn catalog as read-only. Every aggregate read returns an opaque authoring revision that updates must supply; the server atomically rejects stale lesson, question-stem bundle, set, or mock writes so Codex must re-read and reconcile concurrent tutor-web changes. Successful MCP mutations append compact records to the existing activity-event system with the acting tutor, OAuth client, tool, aggregate, before/after revisions, operation kinds, and timestamp; prompts, hidden reasoning, duplicated content, and image bytes are not retained.
